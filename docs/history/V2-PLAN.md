# خطة إعادة بناء موقع «أديب» — النسخة الثانية (V2)

> وثيقة حيّة (Living Document). هذه هي «نقطة الحقيقة الواحدة» لتوجّه إعادة البناء.
> نحدّثها كلما اتفقنا على قرار. آخر تحديث: 2026-07-05.
>
> **✅ قرارات محسومة:** التقنية = **Next.js (React)** · الهوية = **علامة أديب المنشورة تُطبَّق بأمانة** (لونان رسميان من `palette.md`: كحلي `#274060` + فولاذي `#335C81`، خطّا Lyon Arabic + Eras، الشعار والباترن بصيغة SVG) بمعالجة ويب **عصرية جريئة** — لا اختراع هوية. الأصول في مجلد `Adeeb Visual identity/`.

---

## 1) الغاية من هذه الوثيقة

الموقع الحالي ضخم وناجح، لكنه نما عضويًا بلا نظام، فتراكمت عليه ديون تقنية وتصميمية تجعل كل ميزة جديدة أبطأ وأصعب. الهدف: **إعادة بناء كاملة** في «جذر جديد» مع **إبقاء الموقع الحالي يعمل** حتى تكتمل النسخة الثانية، على أساس:

- **هوية بصرية موحّدة** ونظام تصميم (Design System) حقيقي.
- **بنية قابلة للنمو** — إضافة ميزة لا تعني نسخ ولصق ألف سطر.
- **جاهزية للجوال** — أجزاء من الموقع ستتحوّل لاحقًا لتطبيق iOS/Android.

## 2) لماذا نعيد البناء؟ (تشخيص بالأرقام لا بالانطباع)

| المؤشر | الرقم الحالي | الدلالة |
|---|---|---|
| إجمالي أسطر الواجهة | **~132,306** سطر | 43 HTML + 39 CSS + 82 JS |
| أكبر ملف | `admin/dashboard.js` = **7,823** سطر | ملف واحد يصعب صيانته |
| كتل `:root` للرموز | **24** كتلة منفصلة | لا مصدر واحد للرموز |
| متغيّرات CSS | **1,037** متغيّر | موزّعة ومتضاربة |
| ألوان hex مكتوبة يدويًا | **1,802** ظهور / **271** لونًا فريدًا | الهوية يُفترض أن ألوانها ~8 |
| طرق استدعاء الخط | **15+** طريقة (`fr`, `"fr"`, `fb`, `fbb`, `fl`…) | لا نظام طباعة |
| أدوات البناء | **لا يوجد** (كل شيء عبر CDN و`<script>`) | لا modules ولا type-safety |

**أمثلة ملموسة:**
- أكثر أزرق مُستخدَم `#3d8fd6` (236 مرة) **ليس ضمن اللوحة الموثّقة** في `color.md` → الهوية انحرفت عن نفسها.
- **Font Awesome مُحمّل بـ6 إصدارات مختلفة** حسب الصفحة (`7.0.1`, `6.7.2`, `6.5.1`, `6.5.0`, `6.4.0`, `6.0.0`) — دليل قاطع على غياب النظام.
- **486 خاصية `style=` مضمّنة** داخل HTML (منها 211 في `dashboard.html` وحده)، و`@font-face` مُكرّر في **13 ملفًا**.
- **لا هيدر/فوتر مشترك إطلاقًا**: ماركب التنقّل منسوخ ومتباعد عبر 40+ صفحة (لا آلية تحميل مكوّنات).
- `booking.css` و`booking/booking.css` نسختان **مختلفتان**؛ وبقايا مثل `news-workflow-manager-old.js`، `test-insert.html`، `tete/`، و**ملف PDF بحجم 38MB** داخل المستودع.
- عميل Supabase مُعرّف مركزيًا في `supabase-config.js` لكنه **يُعاد تعريفه يدويًا** في `greetings/Eid/script.js` و`test-insert.html`.

> **اكتشاف يقلب الصورة لصالحنا:** يوجد فعلًا نظام رموز محترم في `admin/css/design-tokens.css` (342 سطرًا) وفي رأسه تعليق حرفي: «هذا الملف هو المصدر الوحيد لكل المتغيّرات — لا تُعرّف `:root` في أي ملف آخر». المشكلة أن **19 ملفًا يخالف القاعدة، والموقع العام لا يُحمّله أصلًا**. أي أننا **لا نخترع نظام تصميم من الصفر — بل نُعمّم ونفرض واحدًا موجودًا جزئيًا.** هذا يخفض المخاطرة كثيرًا.

**الخلاصة:** المشكلة ليست في الأفكار بل في **غياب الطبقة المعمارية وفرضها**: النمط الصحيح معروف (بل مكتوب!) لكنه غير مُعمّم. لذلك الترقيع لن يكفي — لكن الطريق أوضح مما يبدو.

**الجانب المطمئن:** الخلفية (Supabase: 65 migration + 7 edge functions) **نظيفة ومنفصلة**، وطبقة الوصول للبيانات (`sbClient` موحّد + `edgeInvoke` بإعادة محاولة ذكية) **جيّدة وتستحق الحفاظ عليها**. نحن نعيد بناء **الواجهة فقط**.

## 3) المبادئ الحاكمة للنسخة الثانية

1. **الرموز مصدرها واحد** (Single Source of Truth): لون/خط/مسافة تُعرّف مرة واحدة وتُستهلك في كل مكان.
2. **المكوّن يُكتب مرة**: `<Button>` واحد، `<Card>` واحد… يستحيل معه وجود 12 شكل زر.
3. **نظام التصميم أولًا**، ثم الصفحات. لا نبني صفحة قبل أن تجهز لبناتها.
4. **أمان الأنواع (TypeScript)**: لموقع ينمو باستمرار، الأخطاء تُكتشف وقت الكتابة لا وقت التشغيل.
5. **ترحيل تدريجي لا انقلاب مفاجئ**: النسخة القديمة تبقى حيّة حتى تكتمل الجديدة.
6. **الخلفية تبقى كما هي**: صفر ترحيل بيانات. نفس Supabase يخدم القديم والجديد أثناء الانتقال.
7. **جاهزية الجوال من البداية**: نختار تقنية ومعمارية تسمح بإعادة استخدام المنطق والرموز في تطبيق لاحقًا.

---

## 4) الإجابة المباشرة على سؤالك: هل vanilla HTML/CSS/JS مناسب لموقع بهذا الحجم؟

**باختصار: لا — ليس بعد الآن، ولثلاثة أسباب تخصّ حالتك تحديدًا:**

1. **الحجم والنمو:** عند 132 ألف سطر ينمو أسبوعيًا، غياب المكوّنات يعني أن كل ميزة = نسخ/لصق + انحراف تصميمي جديد (وهذا بالضبط سبب الـ271 لونًا).
2. **الصيانة:** ملف بـ7,800 سطر بلا modules ولا فحص أنواع = كل تعديل مخاطرة.
3. **مستقبل الجوال:** vanilla لا يعطيك أي مسار مشترك نحو تطبيق iOS/Android؛ ستبدأ من الصفر.

> ملاحظة مهمة: vanilla ليس «خطأ» — هو ممتاز لموقع صغير/متوسط ثابت. مشكلتك أن موقعك **تجاوز** حدوده الطبيعية ودخل نطاق التطبيقات.

## 5) التقنية المقترحة (Stack)

**✅ محسوم — Next.js (React) + TypeScript + نظام رموز عبر Tailwind + بقاء Supabase + PWA، ثم Expo للجوال لاحقًا.**

| الطبقة | الاختيار الموصى به | لماذا |
|---|---|---|
| إطار الويب | **Next.js (React)** | مكوّنات، توجيه، SSR/SEO، أضخم مجتمع |
| اللغة | **TypeScript** | أمان أنواع لموقع ينمو |
| التصميم | **Tailwind كمحرّك رموز** + مكوّنات خاصة | يفرض الرموز، يمنع الانحراف |
| الخلفية | **Supabase (كما هي)** | استثمارك فيها كبير وتعمل للويب والجوال |
| التطبيق (لاحقًا) | **Expo / React Native** | نفس لغة ومنطق الويب → أقصى إعادة استخدام |
| مرحلة وسيطة | **PWA** | تجربة «تطبيق» قابل للتثبيت فورًا وبلا تكلفة |

**لماذا React تحديدًا (وليس Vue/Svelte)؟** لأنك ذكرت تطبيق iOS/Android صراحةً. **React → React Native (Expo)** يمنحك أعلى استمرارية ممكنة: نفس اللغة، نفس طريقة التفكير بالمكوّنات، ونفس الرموز والمنطق يُعاد استخدامها. هذه أقوى قصة «ويب الآن، تطبيق لاحقًا».

**البدائل بأمانة (لو غيّرنا الأولويات):**
- **Nuxt (Vue):** ممتاز للويب، تجربة تطوير أنظف، دعم RTL جيد — لكن مسار الجوال أضعف.
- **SvelteKit:** الأخف والأسرع والأجمل — لكن مساره للجوال هو الأضعف.
- **Flutter:** الأفضل للجوال من كود واحد — لكن Flutter Web سيّئ لموقع محتوى عام (SEO/وصول)، فيصبح لديك تقنيتان.

> إن لم يكن الجوال أولوية، لكنتُ رجّحت Svelte/Vue للبساطة. لكن مع متطلّب الجوال، **React هو الخيار العملي.**

## 6) معمارية المشروع (Monorepo) — ويب الآن، تطبيق لاحقًا

نبني بنية تسمح بإدخال تطبيق الجوال لاحقًا **دون إعادة هيكلة**:

```
adeeb/
├── apps/
│   ├── web/                 # موقع Next.js (نبدأ هنا)
│   └── mobile/              # تطبيق Expo/React Native (لاحقًا)
├── packages/
│   ├── design-system/       # الرموز + المكوّنات المشتركة (قلب الهوية)
│   ├── core/                # عميل Supabase + الأنواع + منطق الأعمال (يُشارَك ويب/جوال)
│   └── config/              # إعدادات مشتركة (eslint, tsconfig, tailwind preset)
├── supabase/                # كما هي بالضبط (functions + migrations)
└── (الموقع الحالي يبقى في مكانه حتى الانتقال)
```

- **الأداة:** pnpm workspaces + Turborepo.
- **الفكرة:** `core` و`design-system` يُكتبان مرة، ويستهلكهما `web` اليوم و`mobile` غدًا.

## 7) نظام التصميم (Design System) — قلب المشروع

هذا ما يحلّ مشكلتك الأساسية. **قيم** الرموز تأتي من **هوية أديب المنشورة الرسمية** (`palette.md`: كحلي `#274060` + فولاذي `#335C81`، وخطّا `Lyon Arabic` + `Eras`) — نوسّع اللونين إلى **مقاييس UI كاملة** (tints/shades) مع إبقائهما المرجع، ونعيد استخدام **بنية** `admin/css/design-tokens.css` كهيكل جاهز، نرفعها إلى حزمة `design-system` ونحذف الـ24 كتلة `:root` المتنافسة. طبقتان:

**أ) الرموز (Design Tokens)** — تعريف واحد يستبدل الـ24 كتلة `:root` والـ271 لونًا:
- **الألوان:** لوحة أساسية (نبني على أزرق `color.md`: `#274060 → #172843`) + ألوان دلالية (نجاح/تحذير/خطأ/معلومة) + رمادِيّات محايدة. لا لون خارج اللوحة.
- **الطباعة:** مقياس واضح بأسماء مفهومة بدل `fr/fb/fbb`. خط **Lyon Arabic Display** (لديك أوزانه الخمسة) بأسماء صريحة: `display / heading / body / caption`.
- **المسافات:** مقياس أساسه 4px. **الزوايا / الظلال / الحركات:** رموز موحّدة.
- **RTL:** خصائص منطقية (`inline-start` بدل `left`) لدعم عربي سليم وقابل للتدويل.

**ب) المكوّنات الأساسية (Primitives):** `Button`, `Input`, `Select`, `Card`, `Modal`, `Badge`, `Table`, `Tabs`, `Toast`, `Avatar`, `Skeleton`… كلٌّ يُبنى من الرموز فقط.

> نتيجة مباشرة: 271 لونًا → لوحة محكومة، و15 طريقة خط → مقياس واحد، و«12 شكل زر» → مكوّن واحد.

## 8) الخلفية (Supabase) — تبقى كما هي

- **لا نلمس قاعدة البيانات ولا الـmigrations ولا الـedge functions.** هي أساس ثابت.
- الميزة الكبرى: النسخة الجديدة تتصل بـ **نفس** Supabase الحيّة → **لا ترحيل بيانات، ولا مخاطرة**. تبديل الواجهة فقط.
- **نحافظ على ما هو جيّد ونعمّمه:** عميل `sbClient` الموحّد وغلاف `edgeInvoke` (بإعادة المحاولة والـbackoff) ننقلهما إلى حزمة `core`، ونُصلح النسختين «الشاردتين» اللتين تعيدان إنشاء العميل (`greetings/Eid`, `test-insert`).
- **ملاحظة مخطّط:** الـmigrations شرائح ميزات لا مخطّط كامل (الجداول الأساسية أُنشئت من لوحة Supabase). لذا في V2 **نولّد أنواع TypeScript من قاعدة البيانات الحيّة** لمخطّط كامل وآمن.

## 9) استراتيجية «الجذر الجديد» والترحيل

1. **نبني V2 في مجلد/فرع جديد** بينما الموقع الحالي يستمر بالنشر من `main` (adeeb.club يبقى حيًّا).
2. **نبني نظام التصميم أولًا**، ثم نرحّل **صفحة بصفحة**.
3. كلا الموقعين يتحدّثان لنفس Supabase أثناء الانتقال (لا انقطاع، لا ازدواج بيانات).
4. عند بلوغ **تكافؤ الميزات (parity)** → نحوّل الدومين إلى V2 ونؤرشف القديم.
5. **بلا انقلاب مفاجئ (no big-bang):** في كل لحظة يوجد موقع يعمل.

## 10) خارطة الطريق (مراحل)

- **المرحلة 0 — الهوية + الأساس:** **استكشاف الهوية الجديدة** (اتجاه بصري: ألوان/طباعة/شخصية) → تحويلها إلى رموز → إعداد الـmonorepo + مكوّنات أساسية + صفحة تجريبية واحدة تثبت المنهج.
- **المرحلة 1 — الصفحات العامة:** الرئيسية، الأنشطة، الأخبار، الدستور، المكتبة، العضوية.
- **المرحلة 2 — الأعضاء:** المصادقة، onboarding، الملف الشخصي، الحجوزات.
- **المرحلة 3 — لوحة الإدارة:** الأكبر — تُقسّم لوحدات (أعضاء/انتخابات/استبيانات/أخبار…).
- **المرحلة 4 — الصقل:** PWA + أداء + SEO + إمكانية وصول.
- **المرحلة 5 (لاحقًا) — الجوال:** تطبيق Expo بإعادة استخدام `design-system` + `core`.

## 11) القرارات

**✅ محسومة:**
1. **التقنية:** Next.js (React) + TypeScript.
2. **الهوية:** نطبّق **علامة أديب المنشورة الرسمية** بأمانة — لونان (`#274060` + `#335C81`)، خطّان (`Lyon Arabic` + `Eras`)، الشعار (أفقي/عمودي + أبيض) والباترن (خطّي/دائري + أبيض) بصيغة **SVG** — بمعالجة ويب عصرية جريئة. الأصول في `Adeeb Visual identity/`. **لا نخترع هوية.**

**⏳ ما تبقّى:**
3. **(اختياري) دليل الاستخدام:** قواعد المسافات/الحجم الأدنى للشعار إن وُجدت — غير معطّلة للبدء؛ الأصول الأساسية اكتملت.
4. **الاستضافة:** Vercel (توصيتي) أم GitHub Pages بـ static export؟ (غير عاجل)
5. **أداة الحزم:** pnpm + Turborepo (توصيتي) — موافق؟

## 12) ما الذي نحتفظ به من الموقع الحالي؟

- **الخلفية بالكامل** (Supabase: قاعدة البيانات + الدوال + الـmigrations).
- **طبقة البيانات الجيّدة:** `sbClient` الموحّد + `edgeInvoke` — نعمّمهما في حزمة `core`.
- **نظام الرموز الموجود:** `admin/css/design-tokens.css` — نرفعه ونعمّمه بدل إعادة الاختراع.
- **العلامة المنشورة كاملة (في `Adeeb Visual identity/`):** لونان رسميان (`#274060` + `#335C81`)، خطّا `Lyon Arabic` و`Eras`، الشعار والباترن بصيغة SVG (مع نسخ بيضاء) — هذا **مصدر** الهوية لا الكود الحالي.
- **المحتوى** ونصوص SEO/Open Graph الجيّدة.

**وما نتخلّص منه:** الملفات المكرّرة/الميتة (`booking/` المكرّر، `tete/`, `test-insert.html`, `clean_css.js`, وأزواج `-old/-new/-enhanced`)، وملف الـPDF بحجم 38MB من جذر المستودع، وتوحيد إصدار واحد لكل مكتبة خارجية.
